# Strategy Studio 2.1 — TRDへの配置比較

## 現行の体験と比較基準

- 入口は `/simulator`。現在の組織から始め、組織図でチームを移動すると別スレッドで再計算する。既存の組織・公式登録は変更しない。
- 主目的は「同じTRDでも継続月額が違う」「同じくらいの人数でも到達までの時間が違う」を理解すること。2,000 IDは固定目標ではなく人数の目安の一つ。
- 比較は「同じタイトル」「同じくらいの人数」「同じ経過時間」の3通り。人数は100・300・500・1,000・1,500・2,000 IDを初めて越えた月を用い、実数を添える。厳密に人数をそろえるための切捨て・再配置はしない。
- 目標タイトルはTRDが初期値。計算範囲は10年から延長可能。未到達なら終了時点の月額と不足条件を表示し、TRD到達の金額として表示しない。
- 図と結果を優先し、成長前提・購入費・資格・サブ作成削除の予定は「前提・詳細設定」へ分離。初期表示で架空のリーダーは追加しない。
- 人・チーム追加、20人一括、リーダー＋10人、1人が1人、3人が3人は入力テンプレート。移動は配下を含む。スマホでは選択→配置先を変更でも同じ操作ができる。元に戻す、基準Aの固定、保存済み案を基準にした比較を提供する。
- 世帯は自分・パートナー・双方の所有サブ。継続月額はライン＋ディレクター＋タイトル。総額、一時報酬、購入費控除後の参考月額は内訳で分ける。

## 配置比較の整合性

- `placementMode: manual` はユーザーが置いた配置を使い、自動探索で別の配置へ差し替えない。
- `placementOverrides` は既存IDの仮想的な配置親変更。紹介者、所有者、既存の成長プロフィールは出発点に固定する。配置だけを動かして成長率が入れ替わることを防ぐ。
- 将来加入する主要リーダーの場所は通常7枠の中で予約する。満杯だからといって別の階層へ黙って移さない。配置先がまだいない場合は加入保留を補足に表示する。
- 循環・起点の移動・通常上限超過を拒否する。暫定のサブ削除による繰上げは従来の明示設定を継承する。
- 比較基準Aは変更せずBだけを編集する。成長や費用なども変えた比較では、その旨を表示する。計算中・変更未計算の結果を最新の数字として見せない。
- タイトル到達後も指定した計算期間を残し、同じ経過月で比較可能にする。到達が期間末なら少なくとも到達後12か月まで計算する。
- 内部上限は在籍・終了を合わせて5,000ノード。タイトル基準の追加人数枠4,999は安全上限であって目標ではない。上限到達時は補足を表示する。最適配置・将来実績の保証ではない。

## 保存と互換性

入力・出発点・結果・ルール版・エンジン版を既存の変更不可リビジョンへ保存する。2.0の保存結果は元のまま開く。再保存は新エンジンで再計算してから行い、旧リビジョンを上書きしない。既存API、従来画面、D1の保存構造は維持する。端末へ個人データを永続キャッシュしない。

## 検証

`src/domain/strategy-canvas.test.ts` は配下付き移動、不変性、紹介者維持、循環・上限、繰上げ例外、予定サブ、成長プロフィールの維持、主要リーダー配置予約、2,000 ID未満でのタイトル到達、経過月比較、概数比較を確認する。現行報酬・API・D1のテストも維持する。

本番への公開・push・本番D1操作は別途承認。下記は2.0実装時の設計記録であり、「2,000 ID固定目標」「3戦略が主画面」という記述は現行UIには適用しない。

# 2.0実装時の設計記録

## 目的と画面

2,000 IDの完成形と、そこへ進む途中の収入・タイトルを同じ前提で比較する。短期の最大ボーナスだけを目標にしない。

1. 現在地・チーム別成長前提
2. 所有ID・費用・資格取得予定・下振れ条件
3. 最短タイトル／完成後の収入／バランスの比較
4. 100→300→500→1,000→1,500→2,000 IDのロードマップと月次内訳
5. 完成形、到達後12か月、タイトル未維持月数
6. 保存、過去の版、実組織を変更しない計画表示

`/simulator`が入口。`/forecast`・`/strategy`はリダイレクト。旧機能は`/legacy/simulator`・`/legacy/forecast`に残す。参考タイトル表は従来どおり補助導線に置く。

## 時間と人数

- 初期計算範囲は120か月。36か月を失敗判定に使わない。10年単位で延長し、同じ出発点と前提で再計算する。
- 計算上の入力上限は12,000か月・在籍と終了を合わせて5,000ノード。事業目標の期限ではなくメモリ・保存容量の保護である。
- 2,000 IDは既存エンジンのタイトル判定と同じ、対象メインの配下にいる当月アクティブID数。本人メインは除く。所有サブ・パートナーは配下にあれば含む。人数とは別に在籍、休止、終了、所有サブを表示する。
- 各チームの最終配分は計算開始前に重みから確定する。既存在籍を起点に残りを配分し、全成長前提で同じ配分を使う。チェックポイントのために再配分しない。
- チェックポイントは閾値を初めて越えた実際の営業月。101 IDで100を越えれば「実数101 ID」とする。人数を恣意的に100へ切り捨てない。低下後に同じ地点へ戻っても初回到達月は上書きしない。
- 到達、計算範囲内では未到達、成長停止、前提未設定を分ける。未到達でも2,000 IDのチーム配分設計は表示する。完成月の報酬は実際にそこまで計算できた場合のみ表示する。
- 未到達時の参考到達月は直近最大12か月の純増の単純延長であり、月次エンジンの到達結果と混同しない。

## 計算の順序と仮定

1. 前月確定状態を使い、予定されたサブ作成・削除・配置変更・資格・コース変更を適用する。
2. チームの開始、紹介、購入継続、休止、退会、再開を確定する。少数の人数は繰り越して、毎月の丸めで小さな退会率が消えないようにする。
3. 当月購入を生成する。現在の版は加入月に初回購入と当月リピートの両方を置く明示仮定である。
4. 下位から上位の順でタイトル取得・維持を判定する。取得済み最高タイトルと当月支給用タイトルは分離する。前月のDR用p.v.は前月の実際の組織で保持する。
5. ID別に5種類のボーナスを計算し、支払先で合算して税・手数料・相殺・繰越を一度だけ処理する。
6. チェックポイントを記録し、完成後12か月の確認を行う。

本人・主要リーダー・サブを含め内部のIDグラフは個別に保持する。表示だけを主要チームにまとめ、p.v.率・円単位端数・同格差額を「代表1人×人数」で近似しない。同じ月の検索用索引はそのスナップショットに閉じ、ユーザー間キャッシュは作らない。

リーダー自身の加入コースと、以降に参加する人のコースは別設定。資格やライセンスは自動で取得済みにせず、明示された取得予定と条件で判定する。下位の紹介は紹介開始までの遅れ・活動率・一人あたり累計紹介上限で制約する。

新規の通常配置は直下7 IDまで。上限に達した時は、そのチーム内を幅優先で探して次の配置先を使い、紹介者を勝手に配置親へ置き換えない。「紹介者IDの比較」を有効にした場合のみ、同じ所有者のメイン・サブの間で新規紹介者IDを比較する。他人への紹介者変更は行わない。

既存リーダーの配置先入力は、本人を移動する指定ではなく、今後その人が紹介する新規IDの配置先を指定する。サブ育成候補では、その所有者の新規紹介をメインと作成サブへ順番に配分する。サブIDを別の人として数え、自動で紹介者が増えることはない。

サブ削除で配下を1段繰上げ、結果的に直下8 ID以上となる例外は利用者提供の暫定ルールであり、明示的に有効にした時だけ試算する。例外が発生しても新規の8人目を直下へ置けない。通常IDの退会は配下を消さず元の段数を保つ仮定であり、通常退会の公式圧縮条件は未確認と表示する。

## 戦略比較の範囲

主要リーダーの配置先を最大8候補から広げ、均等配置の構造指標と安定ID順で最大24状態に絞る。その後、月次報酬を厳密に再計算して選ぶ。許可されたサブ作成案・条件付き削除案・手動案も評価する。

これは有限の候補集合を評価する決定論的な探索であり、全ID・全月のすべての組合せに対する大域的最適解ではない。チェックポイントや下振れ後の結果を見て配置を差し替えることはしない。

- 最短タイトル：初回達成月→未達条件数→同一比較月までの累計収支→安定ID順
- 完成後の収入：完成後12か月の一時報酬を除いた参考収支→完成月の継続収支→同一比較月の継続収支→安定ID順
- バランス：最短案から指定割合（既定20%）以内の遅れで、同一比較月までの累計収支→維持状況→安定ID順

標準の前提で選んだ配置を保守・挑戦・下振れへ再適用する。比較相手の計算終了月が異なる場合は、共通の比較月を画面に表示する。条件が同じなら同じ候補が3目的に選ばれることがある。

## 金額

- 継続報酬：ライン＋ディレクター＋タイトル。維持条件を満たした当月の金額で、保証収入ではない。
- 一時報酬：スタート＋トレーナー。
- 概算受取額：当月総額＋支払先の繰越−控除。3,000円未満の繰越は翌月へ引き継ぐ。
- 参考収支：概算受取額−所有IDの入力済み月額購入費−当月の所有ID初回購入費。新規サブの加入月に初回購入とリピートを計上する仮定なら両方の費用を含む。
- 一時報酬を除いた参考収支：継続報酬だけを支払先単位で概算精算し、購入費を控除する。過去の繰越を混ぜない比較指標。購入費を総ボーナスから直接引かない。
- 過去や将来の税制を推測しない。選択ルールの経過措置テーブルを使用し、長期の価格・報酬率は固定された条件付き試算とする。

## 保存・API・データ保護

`strategy_plans`が計画名と最新の版への参照、`strategy_revisions`と`strategy_revision_chunks`が変更不可の保存内容、`strategy_overlays`が組織画面に表示する選択を保持する。すべて`workspace_id`で分離する。

リビジョンには入力・基準組織・設定データ全体・ルール版・エンジン版・計算結果を保存する。復元では保存済み結果を表示し、現行ルールで黙って再計算しない。「現在の組織から見直す」で最新データを読み直す。入力の指紋は再現性用であり、署名や改ざん検知とは扱わない。

保存は上限12MB、UTF-16サロゲート境界を避けた分割とD1 batchによる一括反映。更新トリガーで過去の版の上書きを拒否する。計算結果はクライアント生成の個人用試算であり、公式精算データとして扱わない。

既存の`members`・`purchases`・`simulation_members`を計画適用時に書き換えない。組織画面に独立した計画表示を重ね、解除で表示だけを戻す。旧`/api/v1`は継続する。

旧保存試算はマイグレーションで元JSON・営業月・ルート・日時を保全し、v2の保存欄から読み出す。旧式に存在しないリーダー別資格・長期前提は推測して補完しない。v2で再計算する際はそれらの入力が必要。

API：

- GET `/api/v2/strategy/context`
- POST `/api/v2/strategy/simulate`
- GET/POST `/api/v2/strategy/plans`
- GET `/api/v2/strategy/plans/:id/revisions`
- GET `/api/v2/strategy/revisions/:id`
- POST `/api/v2/strategy/plans/:id/apply`
- GET/DELETE `/api/v2/strategy/overlay`
- POST `/api/v2/strategy/archive`

画面の重い計算はDedicated Worker内で行い、キャンセル時はWorkerを終了する。サーバーのsimulateは同じ純粋エンジンを使う。APIは既存Access保護を継承しno-store。API・入力・結果をlocalStorage/IndexedDB/Service Workerへ永続保存しない。
